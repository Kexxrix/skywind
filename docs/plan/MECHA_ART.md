# SkyWind 메카닉 디자인·Blender 스프라이트 제작

문서판: **검토 초안 2 / 2026-09-08 KST / 모델·렌더 제작 전**.

사용자는 건담 00의 컨셉을 오마주하기로 결정했다. 현재 흰색·파란색 플레이어 기체와 파일럿의 방향을 기준으로 적·보스도 같은 디자인 계열로 읽히게 만든다. 기존 곤충형 아트 유지와 이미지 생성으로 신규 적을 만드는 초안은 대체한다.

제작 방식은 **Blender 모델링 → 재질·리깅·기믹 애니메이션 → 고정 조건 렌더 → 게임용 스프라이트**로 확정된 방향이다. 구체 기체 구성·실루엣·약점 규칙·프레임 예산은 아래 검토안이며, 문서 전체 승인 전에는 제작하지 않는다.

[1차 전투 감각 확인본](FIRST_IMPLEMENTATION.md)은 현재 적·보스 그림을 확인용으로 재사용하는 별도 범위 제안이다. 이 한정 사용은 새 메카닉의 최종 채택을 뜻하지 않는다. 새 모델·약점/장갑 제작을 첫 플레이 확인의 필수 선행 단계로 두지 않는다.

## 1. 공통 디자인의 기준

현재 SV-01의 중립 프레임을 실제로 확인했다. 흰색/밝은 회색 장갑, 파란 면 분할, 어두운 내부 구조, 청록색의 작은 에너지 발광, 가늘고 각진 비행 실루엣이 현재 기준이다. 파일럿과 SV-01을 이번 요청으로 다시 교체하지 않는다.

사용자가 지정한 건담 00의 오마주 방향을 다음과 같이 작업 가능한 제안으로 번역한다.

| 공통 요소 | 디자인 제안 | 기체마다 달리할 요소 |
|---|---|---|
| 외부 장갑 | 큰 면이 읽히는 단단한 장갑, 사선 절단·겹친 패널 | 면의 비율·장갑 두께·날개/방패의 배치 |
| 내부 프레임 | 어두운 관절·틈·추진 구조 | 움직이는 축·분절 수·기계 밀도 |
| 색과 재질 | SV-01과 같은 정돈된 도장/금속 관계 | 계열별 보조색·명도. 모든 적을 플레이어와 똑같은 색으로 만들 필요는 없음 |
| 에너지 부품 | 핵·발사구·추진구가 같은 기술 계열로 보임 | 핵의 수·위치·개폐 방식·발사구 형태 |
| 읽히는 실루엣 | 작은 화면에서도 기체 역할을 구분 | 사각형·쐐기형·긴 포격형·넓은 장갑형 |
| 세부 밀도 | 보이는 구조와 역할이 있는 디테일 | 단순 드론 → 중간급 → 보스 순으로 구조와 동작 증가 |

공통 DNA는 모든 기체를 동일 모양으로 만드는 뜻이 아니다. 같은 장갑·프레임·에너지 부품의 설계 규칙 안에서 계급과 역할을 나눈다. 건담 00의 특정 진영·기체명·설정을 그대로 게임 세계관으로 도입했다고 가정하지 않는다.

적탄의 위험 색과 기체 재질색은 구분한다. 동일한 기체 계열이어도 플레이어 탄·적탄은 형태와 위험 핵으로 식별되어야 한다.

## 2. 기체 등급과 후보 구성

### 확정된 등급 방향

- **잡몹:** 사각형 형태로 회전하는 단순 드론부터 시작한다.
- **중간급:** 더 높은 기계 밀도, 역할이 읽히는 장갑·무장·가동부를 가진다.
- **보스:** 복잡한 메카닉 구조와 약점 노출·무장 전개·기믹·애니메이션이 필요하다.

중간급/보스를 모두 인간형으로 만들지, 비인간형 비행 메카 중심으로 할지, 일부 변형을 포함할지는 아직 지정되지 않았다. 아래는 공통 부품 언어를 공유하는 드론·비행 메카·대형 병기 중심의 추천안이다.

### 일반 적의 역할 제안

아래 기술 키는 기존 소스의 역할을 추적하기 위한 이름이다. beetle·worm 같은 이름이 앞으로의 곤충 외형을 뜻하지 않는다. 최종 표시 이름과 내부 키의 정리는 실제 구현에 필요한 범위에서 결정한다.

| 역할 | 기존 기술 키 | 새 외형 제안 | 기믹·동작 제안 |
|---|---|---|---|
| 사각 회전 드론 | beetle | 네 모서리 장갑과 작은 중앙 핵, 최소한의 내부 프레임 | 몸체 회전, 발사구의 짧은 충전 |
| 소형 군집 드론 | dragonfly | 같은 부품 계열의 작은 사각/다이아몬드 몸체 | 가벼운 회전·추진 반응, 빠른 격파 |
| 요격 메카 | wasp | 전방이 읽히는 쐐기형 몸체와 두 추진부 | 돌진 전 추진부 전개, 예고 뒤 직선 이동 |
| 장갑 포격 메카 | claw | 넓은 장갑과 가동 포격부 | B02 탄 줄과 맞는 포구 왕복·짧은 반동 |
| 분절 중형 함체 | worm | 연결된 장갑 모듈과 내부 프레임을 가진 긴 병기 | 관절의 제한된 굽힘, 측면 발사구 전개. 생물형 몸통 제거 |
| 기동형 메카 | mantis | 비대칭이 과하지 않은 얇은 기체와 가동 핀 | 이동에 맞춘 핀/추진부 변화 |
| 통로 압박 메카 | ray | 넓은 장갑 패널과 상하 포구 | 두 포구 전개, 중앙의 빈 탄막 통로가 읽힘 |
| 다방향 방사 노드 | orb | 각진 외곽 프레임·중앙 에너지 부품·복수 포트 | 포트의 순차 충전과 방향성 발사 |
| 장거리 포격 메카 | needle | 긴 포신과 뒤쪽 에너지 블록 | 포신 충전·발사 반동·냉각 |
| 장갑 개폐기 — 추가 후보 | sentinel | 슬라이드 장갑 아래의 핵 | 닫힘 → 개방 → 사격 → 닫힘 |
| 분리 모듈 운반기 — 추가 후보 | splitter | 두 소형 드론을 장착한 프레임 | 격파 후 같은 계열 드론 분리 |
| 연결 포격기 — 추가 후보 | relay | 서로 짝을 이루는 사각 프레임 병기 | 연결 예고·동시 포구 전개·한쪽 파괴 후 단독 공격 |

종수는 확정하지 않았다. 기존 9개 행동과 추가 3개 후보를 모두 서로 다른 고밀도 모델로 생산하는 것이 필수는 아니다. 서로 다른 실루엣이 필요한 역할과 공통 모델의 무장/장갑 변형으로 충분한 역할을 R04·R19에서 정한다.

[탄막 4종](BARRAGE_DESIGN.md)의 추천 연결은 방사 노드→B01, 가동 포격기→B02, 분절 포격정→B03, 상하 포격 모듈→B04다. 일반 드론의 기본 조준탄은 실제 발사 때 플레이어 방향을 정한다. 회전 몸체·포구의 애니메이션이 고정된 예고선처럼 보이지 않게 하고, 연속 발사의 모든 탄이 보이는 포구에서 출발하게 한다. 여러 독립 기체가 한 도형을 만들면 각 기체의 공격원을 합산한다.

## 3. 약점과 애니메이션을 전투에 연결

사용자는 약점 노출과 각종 기믹 애니메이션이 필요하다고 했다. 약점 피해 배율·닫힌 상태의 피해·부위 파괴 여부는 아직 확정하지 않았다.

추천 기본안은 **몸통은 계속 피해를 받고, 장갑이 완전히 열렸을 때 노출된 핵에 정확히 맞히면 추가 피해를 주는 방식**이다. 보스전의 약 15초 목표와 강한 무기로 빨리 격파하는 선택을 보존하기 쉽다. 핵 배율은 예를 들어 1.5배를 검토할 수 있으나 현재 확정 수치가 아니다.

L09 텐션을 채택하므로 처치 시간은 정상/텐션·몸통/약점을 함께 검토한다. 텐션 1.5배와 약점 1.5배를 둘 다 선택하면 `1.5×1.5=2.25배`이며 확정 피해 수치가 아니다. 발사 시 텐션 정보와 명중 시 부위 판정을 각각 한 번 적용한다. 약점 노출 시간·L05 HP·15초 목표를 R18·R20에서 함께 검토하며, 텐션 유지를 강제로 요구하는 무적 대기 구간은 자동 추가하지 않는다.

장갑이 닫혔을 때 피해가 전혀 들어가지 않는 방식은 최소 대기 시간·무기 가치·보스 처치 시간을 크게 바꾼다. 이 방식이나 개별 부위 HP를 원하면 L05·R05와 함께 다시 설계한다. 장갑 개폐기 후보의 기존 피해 감소 제안도 R18에서 함께 정하며, 모든 보스에 자동 적용하지 않는다.

### 기본 상태 연결

| 전투 상태 | 모델 동작 | 표시·소리 | 충돌과 피해 |
|---|---|---|---|
| 대기/이동 | 회전·핀·추진부의 평상 동작 | 약한 핵·추진 반응 | 승인된 몸통 판정 |
| 예고/충전 | 포구/장갑이 움직이기 시작 | 발사 방향·충전 빛·짧은 기계음 | 예고가 끝나기 전 공격 피해 없음 |
| 개방 중 | 장갑이 정해진 축으로 열림 | 핵이 드러나는 동작, 과장된 사망 표시 없음 | 약점 활성 시점은 사양에 명시 |
| 개방 완료 | 노출된 핵을 보이는 자세 유지 | 약점 강조 | 최종 승인된 약점 판정만 활성 |
| 발사 | 포구와 반동 동작 | 실제 발사 위치의 섬광·사운드 | 탄 생성은 게임 사건이 결정 |
| 닫힘/회복 | 장갑 복귀·냉각 | 약점 강조 해제 | 활성 종료 시점과 표시 일치 |
| 격파 | 파괴 자세 또는 분리된 큰 부품 | 빛·파편·격파음 | 즉시 피해와 충돌 해제, 점수/보상은 한 번 |

기술 연결의 원칙:

- 게임의 전투 상태와 정규화된 진행도가 애니메이션 프레임을 선택한다. 렌더 프레임이 몇 번 그려졌는지가 발사·약점 개방을 결정하지 않는다.
- 몸통과 핵을 동시에 맞혔을 때 한 발의 피해를 중복 적용하지 않는다. 최종 약점 판정이 우선인지, 관통이 별도인지 명시한다.
- 발사구·약점 중심·반경·피벗은 Blender 모델의 명시적 기준점에서 투영하여 프레임 메타데이터로 보존한다. 그림과 무관한 위치에 손으로 핵을 따로 찍어 맞추지 않는다.
- 가동 중인 발사구는 실제 프레임과 게임 변환에 맞춰 탄과 빛이 나오게 한다. 반동·회전 뒤에도 같은 원점에서 발사한다고 가정하지 않는다.
- 일시정지·저프레임·전환 중에는 애니메이션과 전투 상태가 어긋나지 않아야 한다. 늦게 그려진 프레임 때문에 닫힌 핵에 추가 피해가 남으면 실패다.
- 사각 드론의 회전은 외형 동작이다. 총알 방향·예고를 프레임마다 무작위로 바꾸지 않는다. 실제 발사 포트와 역할을 맞춘다.

## 4. Blender 제작 경로

현재 실행 중인 Blender 연결과 설치 실행 파일의 버전 응답을 확인했다. 열려 있는 파일은 다른 작업의 장면이고 저장되지 않은 변경이 있으므로 건드리지 않았다. 새 기체 제작은 별도 장면/파일이나 독립적인 백그라운드 Blender 프로세스에서 수행한다.

SV-01의 source-manifest.json에는 고정 직교 카메라, 고정 R4 조명, 소스 .blend의 SHA-256, 원본 RGBA 렌더와 피벗 정보가 있다. 현재 SkyWind 저장소에서 SV-01의 .blend 자체는 찾지 못했다. 해시 기록만으로 원본 모델·카메라 수치가 확보됐다고 주장하지 않는다.

원본 .blend를 확보할 수 있으면 그 카메라·조명·재질 규칙을 직접 읽어 공유한다. 확보하지 못하면 현재 승인 프레임을 기준으로 새 제작 장면의 시점·조명·스케일을 맞춘 검토본을 제시한다. 기존 플레이어 모델을 임의로 재구축하거나 교체하지 않는다.

### 제작 순서

1. 사각 드론 1종과 중간급 1종으로 공통 장갑·재질·에너지 부품·게임 시점의 기준을 만든다.
2. 실제 게임 표시 크기와 SV-01 옆에서 실루엣·밀도·색·광원을 비교해 기준을 확정한다.
3. 공통 부품과 재질을 활용해 채택한 적·보스의 고유 구조를 모델링한다. 역할과 무관한 임의 장식은 늘리지 않는다.
4. 개폐 장갑·포구·추진부의 부모/피벗·키프레임을 만들고 약점/발사구 기준점을 함께 둔다.
5. 평상·예고·개방·발사·복귀·격파의 필요한 상태를 같은 카메라·광원·노출·색 관리로 렌더한다.
6. 투명 RGBA 프레임·메타데이터·미리보기와 원본 .blend를 보존한다.
7. 실제 게임 크기로 파생한 프레임을 비교한 뒤 채택·로딩·애니메이션·판정을 연결한다.

사용자 시각 검토는 대표 기체의 기준 확정과 눈에 띄는 개별 보스/기믹에 집중하는 안을 제안한다. 승인된 동일 계열의 작은 파생까지 매번 처음부터 별도 미감 결정을 요구하지 않는다.

## 5. 렌더·스프라이트 규칙

- 카메라는 게임과 맞는 고정 직교 시점을 기본안으로 한다. 플레이어는 오른쪽, 적은 공격 역할에 맞춰 왼쪽을 향하되 몸체 회전형은 실제 가동부의 방향을 따로 확인한다.
- 조명·색 관리·노출·재질 값은 한 제작 장면의 공통 설정을 사용한다. 프레임별 자동 노출·카메라 자동 맞춤을 하지 않는다.
- 각 애니메이션은 전체 포즈를 담는 고정 캔버스·피벗·크기를 사용한다. 프레임마다 잘라 중앙에 다시 맞추면 기체가 흔들리므로 개별 자동 크롭을 하지 않는다.
- Blender의 투명 필름과 RGBA 출력으로 배경 없는 원본을 만든다. 이미지 생성이나 배경 제거로 외형·관절을 보정하는 것을 기본 제작 경로로 사용하지 않는다.
- 몸체·장갑·포구의 입체 변화는 모델과 렌더로 만든다. 빠른 발광·총알·추진 잔상·타격 파편은 게임의 효과층에서 연결해 불필요한 프레임 조합을 줄인다.
- 낮/밤에 모든 애니메이션을 각각 렌더하는 방식을 기본값으로 두지 않는다. 밝은 장갑과 어두운 내부가 두 배경에서 읽히는 공통 조명 기준을 먼저 검토한다.
- 원본 .blend와 RGBA PNG를 보존하고 실행용 WebP/아틀라스·메타데이터를 파생한다. 프레임 크기·압축·아틀라스 여부는 실제 선명도·로딩·메모리 비교 후 확정한다.

미래 경로의 제안은 assets/art/mecha/source/, renders/, runtime/과 tools/render_mecha.py다. 실제 파일은 아직 없다. 다른 작업 폴더에서 모델을 가져올 때는 원본을 그대로 보존하고 출처·복사 위치·해시를 기록한다.

## 6. 제작량과 성능을 통제하는 방식

기믹 애니메이션은 가능하지만 모든 회전각 × 개폐 단계 × 피격 상태 × 낮/밤의 조합을 별도 이미지로 만들면 프레임 수가 크게 늘어난다.

추천은 상태별 필요한 클립을 만들고, 빛·피격 강조를 코드로 합성하며, 단순 회전과 실제 입체 변화가 필요한 회전을 구분하는 방식이다. 사각 드론의 조명·입체감이 중요한 회전은 Blender에서 프레임을 만들고, 게임의 작은 평면 방향 변화는 같은 스프라이트 변환으로 처리할 수 있다.

파일 압축 크기와 실행 중 디코딩 메모리는 다르다. 예를 들어 512×512 RGBA 프레임 60장은 기본 픽셀 데이터만 `512×512×4×60 = 62,914,560바이트 = 60MiB`다. 이는 설명용 예시이며 보스별 확정 프레임 예산이 아니다. 캐시·아틀라스·GPU 사본·밉맵 등의 비용은 별도다.

- 최종 종수·클립별 프레임·실행 크기는 R19에서 하나의 자산 예산표로 확정한다.
- 전 적/보스 애니메이션을 무조건 전부 상주시킨다고 가정하지 않는다. 실제 등장 구간과 다음 보스 준비에 맞춘 로딩·해제 필요성을 검토한다.
- 필요한 프레임을 준비하지 못한 상태에서 보스를 등장시키거나 오래된 곤충 그림으로 대체하지 않는다.
- 이미 원활했다는 모바일·노트북·패드 피드백을 보존할 목표로 삼고, 새 디코딩/합성 비용을 실제 비교한다.
- 고해상도 정지 렌더 한 장으로 채택하지 않는다. 실제 게임 크기·모든 포즈·발사구·약점·밝은 낮/밤을 함께 확인한다.

## 7. 기존 문서와 교체 범위

기존 곤충형 원본·아틀라스는 역사적 제작 자료로 보존한다. 새 완성본의 적·보스 외형으로 계속 사용하라는 보호 규칙은 제거한다. 기존 이미지 생성 기반 신규 적 제작 제안도 Blender 경로로 대체한다.

기존 적의 행동·HP·점수·탄막은 레벨 설계의 미승인 출발점이다. 새 기체 역할·약점과 맞지 않는 부분은 R04·R05·R18에서 조정한다. 이미지 교체만 하고 명중·포구·예고가 옛 위치에 남는 상태는 완료가 아니다.

현재 플레이어·파일럿·배경의 원본과 구현은 이번 문서 반영에서 변경하지 않는다. 문서 전체 승인 이후에도 새 적 제작 때문에 다른 Blender 작업의 장면이나 저장되지 않은 변경을 덮어쓰지 않는다.

## 8. 남은 선택과 합격 조건

- **R04 개정:** 새 기체 역할과 최종 종수. 과거 '기존 9종 외형 유지 + 신규 3종'은 현재 채택안이 아니다.
- **R12 개정:** 제작 방식은 Blender로 정해졌다. 대표 기준·개별 보스의 시각 승인 순서를 구체화한다.
- **R18:** 약점 개방/닫힘의 피해·배율·부위 파괴·개방 시점과 보스 HP 연결.
- **R19:** 인간형/비인간형·변형 정도, 역할별 고유 모델/파생형, 애니메이션·해상도·상주 메모리 예산.

QUALITY의 V42~V46으로 원본 보존·공통 디자인·프레임/피벗·기믹 판정·성능을 확인한다. 현재는 제작 방법과 연결 구조를 설계했으며 실제 모델·스프라이트·기믹은 제작하지 않았다.

## 9. 근거

- 현재 SV-01의 중립 PNG와 source-manifest.json, runtime manifest를 직접 확인했다.
- tools/render_foliage.py에는 별도 백그라운드 Blender에서 원본 .blend와 투명 PNG를 저장하는 기존 제작 예가 있다. 이를 그대로 새 기체 스크립트로 실행하라는 지시는 아니다.
- [Blender 공식 명령행 안내](https://docs.blender.org/manual/en/4.2/advanced/command_line/arguments.html)는 백그라운드 렌더와 프레임/애니메이션 출력의 참고다. 해당 링크는 4.2 문서이며 설치 버전을 의미하지 않는다. 현재 환경은 실행 파일의 버전 응답과 연결 상태까지 확인했으며 새 렌더 작업은 하지 않았다.
